# 概念四：文档分块（Chunking）

## 一、为什么要分块

不能把一整份几十页的 PDF 当成一个整体处理：

1. 一份文档里有很多主题，一个向量无法表达所有内容，语义会被稀释
2. 整篇检索会返回大量无关内容，干扰大模型
3. Embedding 模型有长度限制（通常几百 token）

分块就是把长文档切成一小段一小段，每段聚焦一个具体内容，每块叫一个 Chunk。

分块后：
- 每块只讲一件事，向量表达精准
- 检索命中哪块返回哪块，内容精准
- 省 token、效果好

## 二、分块大小的权衡

### 块太大
- 一个块包含多个主题，语义不单一
- 召回时带入大量无关内容
- 可能超过 Embedding 长度上限

### 块太小
- 上下文被切断，完整的表格、说明被切散
- 句子被拦腰截断，语义残缺
- 检索到孤立的只言片语，无法组织完整答案

### 平衡点
通常 300~800 token 一块，具体取决于 Embedding 模型和文档类型。

## 三、重叠（Overlap）

相邻块之间保留一小段重叠（如每块500字，重叠50~100字）：

- 防止完整语义被切在边界上
- 保证上下文连续性
- 即使关键信息在边界，也会完整出现在一个块里

## 四、常见分块策略

### 1. 固定大小分块
按固定字符数/token 数硬切，简单但容易切断句子和表格。

### 2. 按自然结构分块
优先在段落、句子、标题等天然语义边界切分。

### 3. 递归分块（最常用，Recursive Splitting）
LangChain 的 RecursiveCharacterTextSplitter：
```
先按段落切
  → 还太长，再按句子切
    → 还太长，最后按字符硬切
```

### 4. 语义分块
计算相邻句子的向量，语义发生跳变处切分，效果好但更慢。

## 五、工艺文档的特殊要求

1. **表格不能被切散**：完整的参数表要在一个块里，解析时要先识别表格结构
2. **标题和内容要在一起**：标题不能和对应参数分到不同块
3. **工艺步骤有顺序性**：不能打乱步骤顺序
4. **保留元数据（Metadata）**：记录来自哪份文档、第几页、哪个章节，是引用溯源的基础

每个 Chunk 结构：
```
{
  "content": "45号钢粗车切削速度100~120 m/min……",
  "metadata": {
    "source": "机械加工工艺手册.pdf",
    "page": 142,
    "section": "4.2 车削用量"
  }
}
```

## 六、在流程中的位置

```
PDF文档
  ↓
解析（提取文字、表格、识别结构）
  ↓
分块（切分+重叠）
  ↓
每个块 → Embedding 向量化
  ↓
连同元数据存入向量数据库
```

## 七、为什么对企业级重要

分块直接决定检索质量上限：
- 切得不好，再好的 Embedding 和重排序也救不回来
- 很多 RAG 效果不好，问题出在解析和分块环节
- 对应项目要求第（1）条：文档格式解析
