# 概念六：多轮对话（Multi-turn Dialogue）

## 一、核心问题

用户的追问充满代词、省略和上下文依赖。
- 第1轮："45号钢粗车的切削参数是多少？"
- 第2轮："那精车呢？"

直接拿"那精车呢？"检索会失败：不知道"那"指什么，问题残缺。

## 二、解决思路：历史 + 查询改写

### 1. 保存对话历史
记录之前每一轮的问答。

### 2. 查询改写（Query Rewriting）
把历史和最新问题发给大模型，改写成独立完整的问题：
- "那精车呢？" → "45号钢精车的切削参数是多少？"

改写 Prompt 示例：
```
把最新问题改写成独立、完整、可直接检索的问题，补全省略的主语和代词。
【对话历史】用户：45号钢粗车的切削参数……
【最新问题】那精车呢？
【改写后的问题】
```

## 三、检索和生成用的信息不同

| 步骤 | 用什么 | 为什么 |
|---|---|---|
| 检索 | 改写后的独立问题 | 需要精准完整的查询，不能有代词 |
| 生成 | 完整对话历史 | 保持上下文连贯，回答自然 |

不能直接用整个历史检索：历史里有无关信息，会干扰检索。

## 四、典型情况

1. **指代消解**："那""它"→ 补全具体对象
2. **省略补全**："那铝合金呢？"→"铝合金的粗车参数是多少？"
3. **主题切换**：新问题与历史无关时，不强行套用前面上下文

## 五、对话历史管理

历史不能无限长（受上下文窗口限制）：
1. **滑动窗口**：只保留最近 N 轮（课程项目够用）
2. **历史摘要**：把早期对话压缩成摘要
3. **按需检索**：重要信息已在检索资料中

## 六、完整流程

```
用户第 N 轮提问
  ↓
读取对话历史（最近 N 轮）
  ↓
查询改写 → 独立完整问题
  ↓
混合召回 → RRF 融合 → Cross-encoder 重排序
  ↓
生成 Prompt：系统规则 + 完整历史 + 检索资料 + 当前问题
  ↓
生成连贯回答（带引用）
  ↓
本轮问答追加到对话历史
```

## 七、企业级意义

真实使用中追问、省略、代词是常态，只能单轮回答的系统无法实际使用。
多轮对话让交互接近"向懂工艺的老师傅请教"。

对应项目要求第（4）条：多轮对话。
